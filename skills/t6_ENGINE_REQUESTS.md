# Engine requests from tier 6 (production), 2026-11-19

The engine was not edited. Each item below was worked around inside the t6 skill folders.

1. **render.mjs: send raw frames to ffmpeg instead of PNG files (t6.5, measured).** The engine spends about 73 percent of every frame on `toBuffer('image/png')` (about 70 ms of about 105 ms a frame at 1080x1920). `cv.data()` (raw RGBA) takes 3.8 ms. `t6_5_performance-profiling/module.mjs` has a prototype, `rawRender()`: two worker processes write raw RGBA to stdout, the parent feeds ffmpeg's stdin with `-f rawvideo -pix_fmt rgba`, same filter and x264 settings. Measured on `hello_card` (225 frames): the mp4 is byte-identical to the engine's (sha1 equal), full size 16.0 s -> 5.9 s, preview 8.1 s -> 5.4 s. `framesHash` would need a raw-pixel hash instead of a PNG hash (and t6.2's cache would keep `.rgba` or `.png` as it chooses). Request: make this the default path (keep `--png` for the contact sheet and frame dumps).
2. **canvas.mjs: do the dither natively (t6.5, measured).** `ditherDark` costs about 17 ms a frame (about 16 percent) because it loops over every pixel in JS. A cached noise layer drawn with a blend mode, or a loop over only the near-black rows, should cut it. Needs care: the dither must stay static and deterministic.
3. **README: `toBuffer('image/png', ...)` ignores its options in this @napi-rs/canvas version (t6.5, measured).** Compression levels 0, 1, 3, 6, 9 and a bare number all gave 65 ms and 93,470 bytes. Say so in the README so nobody tries to speed the encode up with a level.
4. **README: Skia records drawing lazily (t6.5, measured).** `card.frame()` returns in about 2 ms; the pixels are made at the first read (about 10 ms for tt10). Anyone timing a card must force a read (a 1x1 `getImageData`). Per-call timers of ctx methods measure recording only.
5. **render.mjs: export the encoder (t6.2).** `VF_YUV`, `X264` and the ffmpeg argument list are not exported, so t6.2's batch renderer and t6.5's raw renderer copy them. Request: export `encodeArgs({fps, frames, preview, input})` (or a `encodeFrames(dir, mp4, opts)` function) so there is one copy.
6. **render.mjs: `loadCard(path, {fresh:true})` (t6.2, t6.4, t6.5).** Node caches imported modules for the life of a process, so loading an edited card twice in one process returns the old code. t6.2 reads META in a fresh child process for this reason. A cache-busting query string on the import URL would cover the card file itself (not its imports).
7. **render.mjs: `--worker` could take a frame list (t6.2).** The worker takes `i0 step last`, so t6.2 starts a process per run of missing frames (chunks of 60). A list or several ranges per process would save about 0.4 s of start-up per chunk.
8. **qc: the "text under 42 px" warning fires on pop-in scaling (t6.1, t6.2, t6.3, t6.4, t6.5).** Chips, tiles and the closer's Follow button scale up from nothing, so each prints a transient warning (under 0.5 s, warning only). Same as t5 item 3; every demo in t6 has between 1 and 16 of these. Request: ignore text whose scale is under 0.9 and whose alpha is rising, or let a card mark an entrance with `decor`.
9. **testkit: an `after` hook (same as t5 item 1).** t6.3 and t6.4 write extra files (cover grid, series sheet) from `checks`, which works because `checks` runs before the render; nothing here needed the hook, but a second output after the render would let the demo's audio-free MP4 and a printable sheet be built in one run.
10. **render.mjs: the frame workers never turn the event loop, so native canvas memory piles up (t6.5, measured).** `--worker` draws its frames in a synchronous loop. @napi-rs/canvas frees a canvas's pixels only after the event loop turns, so every frame's 8 MB stays until the worker exits. Measured with the worker's own loop on `hello_card`: 60 frames peak 1.06 GB, 225 frames peak 3.7 GB; the same loop with `await new Promise(r => setImmediate(r))` every 10 frames peaks at 0.5 GB. A 495-frame card at full size needs about 4 GB per worker (8 GB for two). Request: yield every 10 frames in the worker loop (and in `qcCard`'s frame loop, and in any card tool that draws more than about 60 frames in one process). The t6.4 scorer, t6.5 and the t6.5 raw-pipe prototype already yield.
